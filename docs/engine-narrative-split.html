2  /  The seam

Six functions. The engine never imports anything from game/; the story only ever talks back through these. Both directions ride zustand stores that already exist.

Engine → story (events out)

Fired by the production machine. The story subscribes; the engine never waits on it.

produced(itemName, resource, total) a station finished a unit — the only hook the economy needs
interacted(objectName, characterId) someone worked a station or talked to an NPC
dialogClosed() the panel was dismissed — where the debt hit lands today

Story → engine (commands in)

Plain calls on engine stores. No story concepts cross this line — no debt, no fate, no bricks.

showDialog(text, { blocking, arrow }) blocking pauses production; replaces eventPanelOpen
setWorkSpeed(characterId, multiplier) injuries, already generic in playerStore
setFlag(name, value) reveals gated NPCs; replaces NpcController reading eventsDone

The one check that keeps it honest

Folder structure rots the moment someone adds one convenient import. One test in test/, in the style already there — walk src/js/engine/, fail if any file imports from game/ or data/event.json. Ten lines, no framework, runs with the existing node --test.

That single assertion is worth more than the whole folder move, because it's the only part a future change can't quietly undo.

What this deliberately does not do

No event-emitter class, no plugin registry, no IEngine interface, no separate npm package or workspace. There is one consumer of this engine. A package boundary before a second game exists is a build step you maintain for nobody.

If the actual goal is shipping a second game on this engine, say so — Phase 4 stops being optional and the seam is worth widening. If the goal is "the story is hard to change without breaking production", Phases 1–2 alone fix that.
